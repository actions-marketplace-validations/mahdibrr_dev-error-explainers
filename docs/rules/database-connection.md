# database-connection-explainer — rules

"Can't connect to the database" errors from Node.js apps talking to PostgreSQL
(node-postgres, postgres.js, Prisma, Drizzle). Every rule below was checked
against the primary source named in its row (fetched 2026-09-30). The
connection string itself (encoding, pooler host/port, `pgbouncer=true`,
`sslmode`, Supabase rules) is **database-url-doctor**'s job: when the input
contains a `postgres://` URL, a Supabase host or `sslmode`, this module returns
a `related` pointer to it and never echoes the URL.

**Recognition.** Only exact codes / messages count. The generic Node.js codes
(`ECONNREFUSED`, `ETIMEDOUT`, `ENOTFOUND`, `EAI_AGAIN`, `SELF_SIGNED_CERT_IN_CHAIN`)
are printed by every Node.js client, so they are diagnosed only when the text
also carries a Postgres signal: port 5432 / 6543 (including Prisma's
`` `host`:`5432` ``), a `pg` / `pg-pool` / `postgres` / `@prisma/adapter-pg`
stack frame, a host literally named `postgres` in a getaddrinfo error, a
`postgres://` URL — or `explain({ error, postgres: true })`. PostgreSQL server
messages, Prisma messages and node-postgres' own "The server does not support
SSL connections" identify themselves. Prisma also drives MySQL, SQL Server and
CockroachDB, so a Prisma code is **not** a Postgres signal: without one, the
Prisma findings stay database-neutral (no psql, no `postgresql://`, no
PostgreSQL docs).

| Rule id | Symptom | Cause | Fix | Source |
|---|---|---|---|---|
| `db.econnrefused-ipv6-localhost` | `connect ECONNREFUSED ::1:5432`, with no IPv4 attempt in the text | `localhost` resolved to `::1`; nothing listens on the IPv6 loopback. Since Node.js 17.0.0 `dns.lookup()` returns addresses unsorted ("verbatim") | Use `127.0.0.1`; or `--dns-result-order=ipv4first` / `dns.setDefaultResultOrder('ipv4first')`; or add `::1` to `listen_addresses` | [Node.js dns.setDefaultResultOrder](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder), [PostgreSQL connection settings](https://www.postgresql.org/docs/current/runtime-config-connection.html) |
| `db.econnrefused` | `connect ECONNREFUSED <addr>:<port>`, or `AggregateError [ECONNREFUSED]` listing `::1` and `127.0.0.1` | The target actively refused: no server listening on that port there. Both loopbacks refused → not an IPv4/IPv6 issue. Remote host → `listen_addresses` (default `localhost`) | Start PostgreSQL / fix the port; in a container, `localhost` is the container itself — use the Compose service name + container port, or `host.docker.internal` (Docker Desktop); remotely, check `listen_addresses` | [Node.js common system errors](https://nodejs.org/api/errors.html#common-system-errors), [net autoSelectFamily](https://nodejs.org/api/net.html#socketconnectoptions-connectlistener), [Compose networking](https://docs.docker.com/compose/how-tos/networking/), [Docker networking](https://docs.docker.com/engine/network/), [Docker Desktop host access](https://docs.docker.com/desktop/features/networking/networking-how-tos/) |
| `db.etimedout` | `connect ETIMEDOUT <addr>:<port>` (not `read ETIMEDOUT`) | The other side did not respond in time — unlike ECONNREFUSED, nothing answered | Test TCP reachability from the machine that runs the code; check host and port | [Node.js common system errors](https://nodejs.org/api/errors.html#common-system-errors) |
| `db.enotfound` | `getaddrinfo ENOTFOUND <host>` | DNS failure (EAI_NODATA / EAI_NONAME), or another lookup failure Node.js also reports as ENOTFOUND. A dotless host is often a Compose service name used from outside the Compose network | Resolve with `dns.lookup()` where the code runs; from the host use `localhost` + published port | [Node.js common system errors](https://nodejs.org/api/errors.html#common-system-errors), [dns.lookup()](https://nodejs.org/api/dns.html#dnslookuphostname-options-callback), [Compose networking](https://docs.docker.com/compose/how-tos/networking/) |
| `db.eai-again` | `getaddrinfo EAI_AGAIN <host>` | getaddrinfo "temporary failure" in the OS resolver | Check resolution from the same container / runner; for a service name, check the container is on the Compose network | [libuv errors](https://docs.libuv.org/en/v1.x/errors.html), [dns implementation considerations](https://nodejs.org/api/dns.html#implementation-considerations) |
| `db.prisma-p1001` | ``P1001: Can't reach database server at `host`:`port` `` (or `` `host:port` ``) | Prisma could not connect; credentials never checked | Check the server runs at that address from the machine running Prisma; Docker localhost / service-name rules as above | [Prisma error reference (v6)](https://www.prisma.io/docs/orm/v6/reference/error-reference), [prisma-engines common.rs](https://github.com/prisma/prisma-engines/blob/main/libs/user-facing-errors/src/common.rs) |
| `db.prisma-p1000` | `P1000: Authentication failed against database server …` | The credentials sent are not valid for that server; the network path works | Check the password as it reaches Prisma (encoding → database-url-doctor); try psql with the same credentials; read the server log | [Prisma error reference (v6)](https://www.prisma.io/docs/orm/v6/reference/error-reference), [PostgreSQL Authentication Problems](https://www.postgresql.org/docs/current/client-authentication-problems.html) |
| `db.prisma-p1017` | `P1017: Server has closed the connection.` | Only what the message says: the connection was closed from the server side. Prisma documents no cause | Checks only: server log at that time; same URL with psql / node-postgres | [Prisma error reference (v6)](https://www.prisma.io/docs/orm/v6/reference/error-reference) |
| `db.password-auth-failed` | `password authentication failed for user "x"` | Server reached and willing to talk, but the password for that user did not pass pg_hba.conf's method | Check the password that reaches the driver (encoding → database-url-doctor) and the user; read the server log | [PostgreSQL Authentication Problems](https://www.postgresql.org/docs/current/client-authentication-problems.html) |
| `db.pg-hba-no-entry` | `no pg_hba.conf entry for host "…", user "…", database "…"[, no encryption \| SSL off \| SSL encryption \| SSL on \| GSS encryption]` | No pg_hba.conf line matches. `no encryption` / `SSL off`: the client did not use SSL, so `hostssl` lines cannot match | Unencrypted: enable SSL on the client (node-postgres `ssl`). Server side: add a `hostssl` line (matches SSL connections only; `host` would also accept plaintext), then `pg_reload_conf()` | [PostgreSQL Authentication Problems](https://www.postgresql.org/docs/current/client-authentication-problems.html), [pg_hba.conf](https://www.postgresql.org/docs/current/auth-pg-hba-conf.html), [auth.c](https://github.com/postgres/postgres/blob/master/src/backend/libpq/auth.c) |

| `db.tls-self-signed` | `self-signed certificate in certificate chain` / `SELF_SIGNED_CERT_IN_CHAIN` / `DEPTH_ZERO_SELF_SIGNED_CERT` (with a Postgres signal) | Node.js could not verify the server certificate against its trusted CAs | `ssl: { ca }` in node-postgres (no `sslmode` in the URL); or `NODE_EXTRA_CA_CERTS`. `rejectUnauthorized: false` is flagged as not a fix | [Node.js X509 error codes](https://nodejs.org/api/tls.html#x509-certificate-error-codes), [node-postgres SSL](https://node-postgres.com/features/ssl), [NODE_EXTRA_CA_CERTS](https://nodejs.org/api/cli.html#node_extra_ca_certsfile) |

## Claims left out (no primary source found)

- Firewalls / security groups as the cause of `ETIMEDOUT` — the Node.js docs only say the peer did not respond in time.
- Any Node.js or OpenSSL version for the change from "self signed" to "self-signed" in the TLS message — both spellings are matched, no version is claimed.
- The exact PostgreSQL major versions where "SSL off" became "no encryption" and "non-replication superuser connections" became the SUPERUSER-attribute wording — verified only on REL_13 / REL_15 vs master, so the rules say "older servers".
- A Docker port mapping answering on `127.0.0.1` but not `::1` (a user comment on node-postgres#2643, not documentation).
- Prisma-specific pool advice (single `PrismaClient`, `connection_limit`) and any cause for P1017 beyond its message.
- The Prisma error reference at `/docs/orm/reference/error-reference` no longer lists the P-codes (it documents the newer dotted codes); the v6 reference and prisma-engines are cited instead.
